UI Design Review

OmniVoice Studio · 界面设计评审报告

对 app/app.py 所构建的本地 WebUI 进行整体评审。结论建立在真实渲染与实测数据之上，而非静态代码推断。

界面栈 Gradio 6.30.0 评审日期 2026-10-13 屏幕 音色克隆 / 语音设计 / 音色库 实测环境 1440×1000 · 浅色 + 深色

方法评审是怎么做的

为避开"读代码猜界面"的偏差，本次评审用脚手架把真实组件树与真实 _CSS 跑起来（仅打桩模型加载），再用无头浏览器截图并读取关键元素的计算样式。

① 真实渲染　起 Gradio 6.30 服务，同一份组件树 + 同一份 _CSS，硬件档位与音色库数据走真实代码
② 双主题截图　1440×1000，colorScheme light / dark，全页 + 首屏 + 三个标签页
③ 计算样式取证　对标签、按钮、容器逐一读取 getComputedStyle，取得色值、字号、圆角、尺寸

凡是本报告写"实测"的地方，都附了取到的具体数值，可直接对照复现。

总评六个维度评分

整体判断：设计素养高于一般自研工具，但"设计意图"与"落地结果"之间存在系统性断裂——源码注释里写下的多条规则（标签中性化、次要按钮描边、分组靠间距、右栏粘住、主操作留在首屏）在真实渲染中均未生效。

P0阻断级问题

这四项要么直接违背设计规则，要么对高频使用造成实际阻碍，建议优先处理。

P0-1所有控件标签渲染成靛蓝填充药丸，与"强调色＝可点"的铁律冲突

实测证据
组件标签为 <span class="svelte-jdcl7l">
浅色：bg rgb(224,231,255)　color rgb(30,41,59)　14px/600　padding 4px 6px　radius 6px
深色：bg rgb(79,70,229)　color rgb(241,245,249)　——高饱和靛蓝实心块
根因

CSS 的覆盖打偏了目标。规则写在 .label-wrap 上，而该类只命中 4 个折叠区标题（实测 labelCount=4，且这 4 个的样式确实生效了）；组件标签用的是 Gradio 6 的另一个 scoped 类。同时主题变量 --block-label-background-fill: transparent 在 Gradio 6.30 已不再驱动组件标签。

影响

每个字段的标签看起来像可点的标签 chip / 按钮。浅色下"噪"，深色下高饱和蓝紫块直接抢走视觉焦点——而强调色本应只为唯一的实心动作保留。

修复方案（推荐 a）
  1. 不再依赖 Gradio 内置 label，改用自绘标签（彻底规避内部类名随版本变动）： 
    # label 置空，标签用 HTML 自绘
gr.HTML('<p class="ov-field-label">语种</p>')
gr.Dropdown(label="", show_label=False, ...)
    /* 自绘标签：中性小字，不是药丸 */
.ov-field-label{margin:0 0 4px; font-size:13px; font-weight:600;
  color:var(--ov-text-muted); letter-spacing:.01em}
  2. 若坚持覆盖：需按结构选择且接受版本风险（svelte-* 哈希会变），不推荐： 
    .gradio-container .block > .container > span:first-child{background:none!important;padding:0!important}

P0-2首次启动界面完全不出现——模型加载把 UI 构建阻塞住了

实测证据
入口顺序：load_model() → build_ui() → launch()（位于 __main__）
权重体积：主模型约 2.3 GB + Whisper 约 1.6 GB（README 自述）
影响

用户双击 run.bat 后，浏览器打开发现在长时间内是"无法连接"，而非"正在加载"。等待可能达数十秒至数分钟，且无任何进度——这是最容易劝退的一处。

修复方案
  1. 把服务先起来、模型后加载：让 build_ui() 不依赖模型即可构建，用 demo.load() 事件异步加载并把状态渲染到顶部提示条。 
    with gr.Blocks() as demo:
    boot = gr.HTML('<p class="ov-hint">正在加载模型…</p>')
demo.load(fn=load_model_and_report, outputs=boot)   # 页面先可见
demo.queue().launch(...)
  2. 硬件档位探测很快，可保持同步；只把权重加载异步化。
  3. 加载中给出可辨识的阶段文案（"加载权重 → 初始化设备 → 就绪"）。

P0-3主操作「生成语音」跌出首屏

实测证据
音色克隆页：按钮顶部 top = 1042 px（视口高 1000 px）　页面总高 1532 px
即：1440×1000 下必须滚动才能看到主操作；1366×768 的笔记本更严重
根因

单列纵排把「语种(110px) → 文本域 → 音色来源折叠区 → 参考音频(126px) → 参考文本 → 存为音色」依次堆叠，主按钮排在必填项之后但仍在参考音频之后；而注释中"主操作紧跟必填项，不等折叠区展开就能点到"的目标与实测不符。

修复方案
  1. 把主按钮上移到文本域之后、参考音频折叠区之前——先"写什么"，再"用什么声音"。
  2. 「音色来源」默认 open=False（当前为 True，撑高首屏）。
  3. 或按 P1-1 在宽屏改两栏，主按钮随左栏自然进入首屏。
  4. 可选：窄屏下把主按钮做成底部 sticky 操作条。

P0-4深色模式下"次要按钮"渲染成实心靛蓝——且它还是禁用态

实测证据
深色 secondary：「保存到音色库」bg rgb(99,102,241)　color #fff　opacity .5　disabled=true
浅色对照：bg rgb(241,245,249)　opacity .5　disabled=true
影响

一是违背设计注释"次要按钮走描边而不是填充：一个视图里只留一个实心动作"；二是"禁用"与"醒目"同时出现——一个不可点的实心主色按钮，用户会反复去点。

修复方案
  1. 显式给次要按钮落地描边，别只设颜色变量（当前 border-width 实测为 0）： 
    .gradio-container button.secondary{
  background:transparent!important;
  border:1px solid var(--ov-border)!important;}
  2. 禁用态用降饱和 + 降对比，而非只降透明度：给出专门的 :disabled 规则（灰底、灰字、无阴影）。

P1重要问题

影响信息效率与观感一致性，建议紧随 P0 处理。

P1-1单栏 880px + 强制纵向：横向空间浪费约 39%，且三处布局代码失效

实测证据
容器宽 880px（视口 1440px → 两侧各留 280px）
.ov-main-row 计算值 flex-direction: column（CSS 显式强制纵向）
但源码里仍写着 gr.Column(scale=3) / scale=2，注释还写着"宽屏下粘住，左栏滚长表单时结果不会跑出视野"
影响

宽屏用户看到大片空白；scale=3/2 与"右栏粘住"成了永远不会执行的死意图；结果区被压到表单下方，合成后需要滚动才能看到/试听。

修复方案
  1. 恢复"左表单 / 右结果"两栏，并加断点：宽屏两栏、窄屏回落单栏。 
    /* 默认单栏 */
.ov-main-row{flex-direction:column;gap:20px}
/* ≥1180px 才并排，并给结果栏 sticky */
@media (min-width:1180px){
  .gradio-container{max-width:1180px!important}
  .ov-main-row{flex-direction:row;align-items:flex-start}
  .ov-main-row > *:last-child{position:sticky;top:24px}
}
  2. 若确定保持单栏，则删掉 scale= 参数与 sticky 注释，消除死代码。

P1-2层级倒置：章节标题比字段标签还小

实测证据
章节标题 .ov-sect：13px / 600
字段标签：14px / 600　→ 章节 < 字段，层级关系反了
页标题 h1 .ov-title：仅 16px / 600；meta 行 12.5px
修复方案
  1. 建立可辨识的字阶，拉开跨度而非全部挤在 12.5–16px： 
    /* 语义 → 尺寸（放大跨度） */
h1/.ov-title ……… 20px/700   /* 页面锚点 */
.ov-sect ………… 15px/700   /* 章节标题，须 > 字段标签 */
.ov-field-label … 13px/600
.ov-hint/.ov-meta 12.5px/400
  2. 章节标题加一点上边距（如 margin-top:6px）配合字号，形成分组感。

P1-3音色库：同一份列表在三处重复出现

实测证据
同页同时存在：①「选择音色」下拉　②「音色/参考文本」表格　③「批量选择」复选组
三者数据源相同（均为 list_voices()）
影响

用户要先用下拉"选中"才能试听/重命名，又要到另一个复选组里勾选才能删除——同一个对象有两套选择机制，认知负担与误操作同时上升；表格却不可交互，成了纯展示的冗余。

修复方案
  1. 以表格为唯一入口：把表格做成可选行（行内提供「试听 / 重命名 / 删除」操作），移除独立的复选组。
  2. 若保留批量删除：用表格自带的行选择 + 一个"删除所选"按钮，确认走 Modal（列出将删除的名称），替代当前的"勾选确认"复选框。
  3. 「选择音色」下拉与表格二选一即可，避免两套选中态互不同步。

P1-4音色库纵向空洞约 120px

实测证据
「重命名」行底部 → 数据表格顶部，实测间距约 120px（见 图 3）
根因

.ov-main-row 被强制为纵向后，原本并排的两列变成上下堆叠，两段内容的固有高度差在栅格拉伸后暴露成空白。

修复方案
  1. 按 P1-1 恢复两栏（宽屏）后此空白自然消失——左侧放"选中详情"，右侧放列表与删除。
  2. 若坚持单栏：调整该页的父子顺序，让"选择音色 → 详情 → 列表 → 批量操作"成为连续流，不给纵向 Row 制造拉伸机会。

P1-5禁用态可读性不足

实测证据
浅色 secondary 禁用：bg rgb(241,245,249) + opacity .5 → 文字与背景对比进一步衰减
「保存到音色库」在浅色下近乎不可辨
修复方案
  1. 禁用态不使用整体 opacity，改为显式的灰底/灰字（仍满足 4.5:1 的可读下限），并去掉悬停位移。
  2. 无法点击的原因应就近说明——例如"保存"旁常驻一行 .ov-hint：「上传参考音频后可保存」，而不是让按钮默默变灰。

P1-6"分组靠间距，不靠框线"未落地：每个字段仍套着独立方框

实测证据
每个组件被 Gradio 包成 .block.padded（padding 10px + 1px 边框 + 圆角）
克隆页可见约 8 个独立方框依次排列（见图 1）
影响

与注释"分组靠间距，不靠框线"直接冲突：8 个框 = 8 条分隔线 + 8 组内边距，界面读起来"碎"且纵向被撑长（也是 P0-3 的共因）。

修复方案
  1. 统一去掉 block 的边框与背景，只保留输入控件自身的边界： 
    .gradio-container .block.padded{
  border:none!important; background:transparent!important; padding:0!important}
  2. 分组改用 .ov-stack 的间距（组内 10px / 组间 20px）表达，与既有设计说明一致。

P2打磨项

不阻断使用，但决定"精致感"能否成立。

P2-1圆角三套值并存

实测证据
block 圆角 8px　按钮 6px　标签 6px　部分 padded block 0px
而 CSS 已声明 --ov-radius-control: 8px——未传导到按钮（按钮取的是主题 radius_md=6px）
修复方案

统一到一个值（建议 8px）：把主题 radius_size 设为 radius_lg，或在 CSS 里显式覆盖按钮圆角，保证"一处定义、处处一致"。

P2-2info 语义色与中性边框几乎同色

实测证据
--ov-info-bg: oklch(0.965 0.003 265)、--ov-info-bd: oklch(0.890 0.006 265)
色度仅 0.003 / 0.006 → 与普通边框/底色难以区分，"提示"失去语义
修复方案

把 info 的色度提到 0.03–0.05，并选一个与 accent（275°）明确区分的色相（如 230° 蓝或 200° 青），使其"是提示"一眼可辨——注意仍要与 accent 保持区分度。

P2-3自定义 oklch 强调色与 Gradio 主题 indigo 不完全一致

实测证据
主按钮：oklch(0.52 0.17 275)；主题 primary_hue=indigo 生成的边框色 rgb(99,102,241)
两者色相接近但不相等 → 自定义按钮与主题生成的其它元素可能出现细微色差
修复方案

要么只信主题（全部引用主题变量，不自持 accent），要么只信令牌（把主题的 primary_hue 也用同一 oklch 定义并把所有相关变量对齐）。当前"两套并存"是最容易产生色差的组合。

P2-4标签命名风格不统一（中英混排 vs 纯中文）

实测证据
「性别 Gender」「中文方言 Dialect (中文)」　对照　「语速」「降噪」「推理步数」「固定时长（秒）」
修复方案

统一为「中文（英文）」或纯中文一种风格。建议中文主标签 + 英文小字副标（如"性别 Gender"），既保风格统一，又保留原清单的可检索性。

P2-5文本域行长过宽 / 生成中缺少段级进度

说明

单栏 880px 下正文输入行长超过舒适阅读区间（建议 65–80 字符以内，即约 640–720px）。长文本合成是"分段串行"的，show_progress="full" 只是 Gradio 的遮罩，用户无法知道"第几段 / 共几段"。

修复方案
  1. 正文文本域单独限宽（如 max-width:720px），其余控件保持满宽。
  2. 分段合成时通过 gr.Progress 上报"第 n/total 段"，让等待有确定性。

P2-6源码注释与实现不符，形成文档债

实测证据
注释称「宽屏下粘住」→ 无 sticky 规则；「两列网格」→ 但父级被强制为 column；
「主操作紧跟必填项…不等折叠区展开就能点到」→ 实测 top=1042px 在首屏之外
修复方案

按本次修复逐条对齐注释；能落实的落实，落实不了的删除。这类"写着但没做"的注释会持续误导后续维护者。

清单落地检查表

  • 弃用 Gradio 内置 label，改为自绘中性标签（label="" + .ov-field-label）
  • 启动改为"服务先行、模型异步加载"，加载中在页顶显示阶段文案

  • 宽屏（≥1180px）恢复左表单 / 右结果两栏，结果栏 sticky；窄屏单栏
  • 字阶重排：页标题 20px / 章节 15px / 字段标签 13px / 提示 12.5px
  • 音色库收敛为"表格即入口"，删除重复的复选组，删除确认改用 Modal
  • 统一圆角至 8px；去掉 .block.padded 的边框与内边距，分组靠间距
  • info 语义色提升色度并与 accent 拉开色相
  • 统一标签命名风格；正文文本域限宽至 720px
  • 长文本合成分段上报进度（第 n / 共 m 段）
  • 清理与实现不符的源码注释

值得保留的部分

  • 状态提示三重编码：颜色 + 图标 + "成功/注意/失败"文字标签，并用 role="alert" / role="status" 区分紧急度——比多数自研工具扎实。
  • 焦点环（:focus-visible）、减少动效（prefers-reduced-motion）、高对比模式（forced-colors）均有处理。
  • 破坏性操作有护栏：删除需勾选确认，提示中列明具体名称。
  • 按钮按条件禁用：无参考音频时"保存"不可点，避免"点了才知道不行"。
  • 表格数字用等宽（tabular-nums）、不引外部字体（离线可用）——细节意识在线。
  • 设计令牌化的意识：已把强调色/语义色/焦点环收敛成变量，本次问题主要是"覆盖目标打偏"，而非缺乏体系。
